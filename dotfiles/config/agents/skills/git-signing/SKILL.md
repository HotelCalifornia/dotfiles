# Git Identity & Signing

Identity is split deliberately:

- `~/.gitconfig` — deployed by the `git` profile. Shared across machines, minimal,
  sets `user.useConfigOnly = true`, and includes the machine-local file.
- `~/.config/git/identities.gitconfig` — the machine's **default** identity, plus
  one `includeIf "hasconfig:remote.*.url:…"` per additional identity.
- `~/.config/git/identities/<name>.gitconfig` — each additional identity.

All three are generated per machine by `init-profile.py --identities` and are
**never committed**. Files start with `# Generated by init-profile.py
--identities`; the wizard only deletes files carrying that marker, so
hand-written ones are left alone. Do not hand-edit generated files unless the
wizard cannot run; rerunning it reads the existing files back.

## Diagnose first

```bash
# Which identity is actually in effect, and where does it come from?
git config --show-origin --get user.email
git config --show-origin --get user.signingkey
git config --show-origin --get-all include.path
git var GIT_AUTHOR_IDENT          # name/email/time git would use now

# Is a commit signed, and by which key?
git log --show-signature -1
git verify-commit HEAD            # current commit only

# Local key material
gpg --list-secret-keys --keyid-format long <keyid-or-email>
gpg --with-keygrip --list-secret-keys <keyid>   # keygrip, needed for pinentry cache
gpg --export --armor <keyid> | gpg --show-keys --with-fingerprint
```

`user.useConfigOnly = true` means git refuses to commit without a resolvable
identity rather than guessing `user@hostname`. That is intentional; configure an
identity instead of disabling it.

## Adding or changing an identity

Preferred (needs an interactive terminal — agents must hand this to the human):

```bash
~/.local/bin/init-profile.py --identities
```

It edits the default identity, adds/removes extra identities matched by remote
URL, and picks or generates GPG/SSH keys. Then make sure the shared config is
deployed on this host:

```bash
dotdrop install -f -p <hostname> f_gitconfig
```

Details that are easy to break:

- Additional identities without a key set `gpgsign = false` **and** an explicit
  `signingkey = <email>`, so `git commit -S` fails rather than silently signing
  as the default person. Do not "simplify" that.
- SSH identity uses `core.sshCommand = ssh -i <key> -o IdentitiesOnly=yes`; this
  is what lets two accounts coexist on one host.
- `includeIf` patterns are globs matched against the remote URL and are
  case-sensitive. GitHub remotes appear as both `github.com/Owner/...` and
  `github.com/owner/...`; match the case actually used by clones.
- A second machine-local identity file exists only if you added extra identities;
  the include is ignored when missing.

## GitHub key registration

```bash
gh auth status                     # shows token scopes
gh api /user/gpg_keys --jq '.[] |
  {key_id, name, emails: [.emails[] | {email, verified}]}'
gh gpg-key add <public-key.asc> --title "hostname"
```

- **Scopes:** adding needs `write:gpg_key`; deleting needs `admin:gpg_key`.
  `gh auth refresh -h github.com -s admin:gpg_key` (or a fresh login) adds it.
- **Replace, don't update:** GitHub cannot edit a key. Delete the old copy, then
  add the new export. Re-adding without deleting fails with
  `HTTP 422 … one or more subkeys already exist`.
- The key's email must be verified on the account. Check the `verified` flag in
  the listing above.
- Removing a UID does not change the key material or fingerprint, so previously
  signed commits keep verifying. GitHub only needs the updated export uploaded.

## Outdated or unwanted UID on a key

Revoking a UID does **not** remove it: gpg still lists it and pinentry still
displays it. To strip it:

```bash
# 1. Back up the secret key first
mkdir -p ~/.gnupg/backups && chmod 700 ~/.gnupg/backups
gpg --armor --export-secret-keys <keyid> > ~/.gnupg/backups/<keyid>-$(date +%F).asc
chmod 600 ~/.gnupg/backups/*.asc

# 2. Verify UID order, then delete the unwanted one (1-based, as shown by edit-key)
gpg --list-secret-keys --with-colons <keyid> | grep '^uid'
printf 'uid <N>\ndeluid\ny\nsave\n' | gpg --batch --command-fd 0 --edit-key <keyid>

# 3. Verify, then re-export and replace the GitHub copy
gpg --list-secret-keys <keyid>
gh gpg-key delete <api-id> && gh gpg-key add <clean-key.asc>
```

Use the colon listing to confirm the index before deleting; indexes shift when
UIDs are removed. After stripping, keyservers may still publish the old UID
(they cannot forget); the local keyring and GitHub copy are what matter in
practice.

## Passphrase prompts

The prompt text is a `SETDESC` string built by gpg from the **keyring UID**. If it
shows a name that no longer appears in `gpg --list-secret-keys`, the stale name is
coming from the passphrase cache, not the key.

On macOS, `pinentry-mac` caches the passphrase in the login Keychain as a generic
password:

- service `GnuPG`, account = the key's **keygrip**
- the item's **label** is a snapshot such as `"Name <email> (KEYID)"`, taken when
  it was saved

That label is what macOS/Keychain access dialogs display, so a renamed or
stripped key can still prompt with the old name — often twice, once per access.
Diagnose and fix:

```bash
security dump-keychain 2>/dev/null | grep -B3 -A10 'GnuPG'   # label + acct
security delete-generic-password -s GnuPG -a <keygrip>      # drop stale item
gpgconf --kill gpg-agent                                    # clear in-memory cache
```

The next signature prompts once for the passphrase; if "save in keychain" is
chosen, pinentry-mac recreates the item with the current label. On Linux,
`gpgconf --kill gpg-agent` (or `gpg-connect-agent reloadagent /bye`) clears the
agent cache; the pinentry backend's cache depends on the desktop.

Never paste a private key into chat or a commit. Export armored **public** keys
only; keep secret-key backups mode `600` outside the repo.

## Troubleshooting

| Symptom | Likely cause | Check / fix |
| --- | --- | --- |
| `gpg failed to sign the data` | key missing from keyring, agent/pinentry problem | `gpg --list-secret-keys <keyid>`; retry with `gpgconf --kill gpg-agent` |
| GitHub shows **Unverified** | key not uploaded, wrong key, or email unverified | compare `gpg --show-keys` fingerprint to `gh api /user/gpg_keys`; verify email |
| Commit authored as the wrong person | extra identity's `includeIf` doesn't match the remote URL | `git config --show-origin --get user.email`; check URL case/pattern |
| Prompt shows an old name | UID still on the key, or stale Keychain item label | `gpg --list-secret-keys`; `security dump-keychain`; delete keychain item |
| `422 subkeys already exist` | old copy of the same key still on GitHub | `gh gpg-key delete <id>` first (needs `admin:gpg_key`) |
| Commit refused with no identity | `useConfigOnly` and identities file missing | run `init-profile.py --identities`, then reinstall `f_gitconfig` |
| `--identities` exits immediately | no interactive TTY | hand off to the user; do not fake a TTY |

## Done means

- `git config --show-origin --get user.email` resolves through
  `~/.config/git/identities.gitconfig`.
- `gpg --list-secret-keys <keyid>` shows only the intended UID and the expected
  fingerprint.
- `git log --show-signature -1` reports a good signature for the expected key.
- `gh api /user/gpg_keys` lists that fingerprint, with a verified email.
- No stale Keychain item or agent cache is still surfacing an old description.
